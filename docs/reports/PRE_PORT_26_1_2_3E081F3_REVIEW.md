## 质量判断

正面：磨损、来源、选项目录已有独立模块；磨损/来源提供可测的纯函数；配置保留 raw datapack 与有效值两个层次；代码通过参数约束处理多个关联选项；Mod Menu shim 明确设置不进入 binary/sources JAR。

## 必须修复的技术问题（不是让用户选择是否保留 bug）

### 1. 配置界面会重新引入旧鼠标编号问题【高，移植阻断】

源 `ChiseledEnchantingConfigScreen.java:709–755`：左键判断为 `event.button() == 0`，右键为 `== 1`，拖动也判断 0。

26.3 当前路径使用 SDL/平台常量，左 1、右 3。照搬可能使左键误触右键动作、滑块不响应。新配置界面及其他新增鼠标入口必须统一使用平台常量，并扩大现有回归覆盖。

[源代码](https://github.com/q14433686-arch/chiseled-enchanting-table-26.1.2-source/blob/3e081f31f262dc13f6a92f0a50313e12f6af28c0/src/client/java/chiseled_enchanting_table/gui/config/ChiseledEnchantingConfigScreen.java#L709)

### 2. LAN 配置管理权限过宽【高，安全边界】

源 `ModConfigNetworking.canPlayerManageConfig()`：只要 `!server.isDedicatedServer()` 就返回 true；更新包 receiver 使用同一判断。这不区分整合服务器的房主与加入 LAN 的访客。不能依赖客户端 UI 隐藏按钮来充当服务端授权。

移植时应在服务端明确校验房主/有权限玩家；拒绝未授权包，不影响其只读查看配置。具体权限 API 还须对照 26.3 实现。

[源代码](https://github.com/q14433686-arch/chiseled-enchanting-table-26.1.2-source/blob/3e081f31f262dc13f6a92f0a50313e12f6af28c0/src/main/java/chiseled_enchanting_table/config/ModConfigNetworking.java#L64)

### 3. 现有 wire 不能原样接收新字段【高，移植阻断】

源新增 `TransformationDisplay.unlocked`、opening/live 的 `cramped_library`，cost/config 又增加退款、书架和母本参数。但源仍使用 26.1.2 的集合 helper，且不能替代本地已有的长度限制、live `container_id`、目录同步和 revision 通道。

移植应逐字段合并：保留本地限幅和目标菜单判断；为下一次真实 wire 变化更新独立协议标识及受影响通道；加入新 runtime config 包的能力检查。发布文字仍可为 1.1.0。**不可直接把源文件覆盖过来，也不可因改版本号而回退协议。**

### 4. 配置“已保存”和持久化成功不是一回事【中高，可靠性】

源 `setLocalAndSave` 先替换内存配置；`saveToDisk` 直接打开目标文件写入，失败只记录 WARN、不返回失败状态；随后仍会广播配置。配置 GUI 也在服务端确认前更新 baseline/本地远端缓存。由此可能出现当前运行生效、重启后丢失，或 UI 先显示成功的情况。

建议：临时文件 + 替换写入、明确保存结果、服务器确认/错误反馈；畸形配置 JSON 受控拒绝，不能用无条件成功提示掩盖异常。不要把这一问题描述为已实测服务端崩溃。

[持久化代码](https://github.com/q14433686-arch/chiseled-enchanting-table-26.1.2-source/blob/3e081f31f262dc13f6a92f0a50313e12f6af28c0/src/main/java/chiseled_enchanting_table/config/ModRuntimeConfig.java#L193)

### 5. 配置有多条应用路径，必须保持服务端权威【中高，状态一致性】

源 GUI 的 `SINGLEPLAYER_LIVE` 分支先在客户端直接 `ChiseledEnchantingTableData.applyRuntimeConfig`，再把同一更新排入整合服务器；`applyAndBroadcast` 又分别发送 runtime config、费用，刷新 live，但不是更新所有开屏字段。客户端、整合服务器共享这些静态表时，不能把多次调用当作一个原子配置发布。

此外，本地 26.3 通过重载时关闭菜单消除了旧转化快照；源新增的“实时配置”路径如果只刷回调/live，会绕过这一保护。

移植最小原则：服务端提交有效状态，客户端接收快照；变更影响开屏数据时明确关闭/重开或完整更新快照。不得仅刷新 UI 回调就声称规则已同步。

### 6. 解锁判定与全局目录有语义冲突【中高，移植设计接口】

源 `buildTransformationDisplays(player)` 将 `unlocked` 放入转化描述，且 null player 对有门槛规则返回锁定；本地查看器已改为消费服务端权威目录。合并时必须由实际 ServerPlayer 构建其目录，并在解锁状态变化时失效相应缓存。

不能继续调用无玩家版本后把全员锁定结果当作权威，也不能让一个玩家的解锁状态覆盖另一个玩家。开屏、操作校验、配置变更和查看器使用同一判定来源。

## 需要用户选择的设计取舍

### A. 配置与 datapack 谁优先？

源 `Draft.overrideDatapacks = true`；`shouldApplyKey` 在 true 时对全部管理字段生效。因此默认配置也可能覆盖整合包 datapack 中的同名规则。这是源侧明确默认，不应简单称为解析 bug，但与“datapack 是权威规则”方向不同。

可选：忠实保留源默认；改为 datapack 优先/仅显式编辑字段覆盖；进一步拆分全局启动配置、世界运行规则和客户端显示偏好。源文件位于实例全局 `config/chiseled_enchanting_table.json`，也不是自动按世界隔离。

### B. 旧物品的来源与退款怎么迁移？

源 `getPaidSlices` 在缺少 `cet_provenance` 时返回空集，退款把这些等级视为外部来源，默认比例 0.25。旧版合法表内制作的物品也没有标签，因此无法准确追溯；实际退款变化由势能表与取整决定，不能简单宣称所有物品都精确减少 75%。

可选：统一严格按未知/外部处理，强化新经济边界；或提供旧档兼容退款配置，保留旧体验，但必须承认未标记外部物品也会享受宽松规则。不能伪造“能自动识别所有旧表内物品”的迁移。

[缺失标签处理](https://github.com/q14433686-arch/chiseled-enchanting-table-26.1.2-source/blob/3e081f31f262dc13f6a92f0a50313e12f6af28c0/src/main/java/chiseled_enchanting_table/mechanics/enchanting/EnchantmentProvenance.java#L74)

### C. 新玩法默认立即生效，还是旧档兼容模式？

源默认 wear/16/4/step_down、12/32 门槛和空间约束，会改变现有书库的可用性与维护成本；通用批处理也改变原来一次一件的操作预期。它们不是编译兼容补丁，需明确选择默认策略。

## 可选实施方向（等待用户决定）

| 方向 | 实施范围与默认策略 | 优点 | 代价 |
|---|---|---|---|
| **方案 1：忠实全量移植 + 必要加固** | 全量移植新玩法和配置 UI，保留源默认（配置覆盖 datapack、母本磨损、严格未标记退款等）；修复上述确定技术问题，保留全部 26.3 防线 | 与 26.1.2 新版行为最一致，后续同步成本较低 | 旧档的退款、书库布局和母本消耗会变化；上线前需明确迁移提示 |
| **方案 2：全量功能 + 旧档兼容默认** | 功能全部提供，但采用 datapack 优先、默认 keep 母本、兼容退款和旧门槛/布局；新规则通过明确配置启用 | 对已有整合包和世界冲击较小 | 默认行为不再与源版一致；宽松未标记退款延续旧经济风险，配置/测试矩阵更大 |
| **方案 3：先整理配置/状态架构，再全量移植** | 先分离启动、服务端有效规则、客户端偏好；统一校验/持久化/确认、权威快照与每玩家解锁，再接 D1–D7 和 UI；玩法默认需单独选择源版或兼容档 | 长期边界最清晰，减少新增同步路径互相冲突 | 改动范围和验证工作最大，不是一次简单同步 |

**建议：** 如果首要目标是“跟上 26.1.2 的全部新内容”，选择方案 1，但必须接受其旧档规则变化；若主要服务已有世界/整合包，选择方案 2；如果准备长期维护配置体系，选择方案 3。没有在本次预先替用户选择其中任何一个。

无论选择哪个方向，版本号均保持 1.1.0；鼠标、权限、坏包防护、持久化失败反馈等技术问题均不作为可选保留项。
