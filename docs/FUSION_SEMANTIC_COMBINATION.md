# 融合设计：取词眼，但要说明怎样结合

> 用户提出：可以从附魔的不同词眼或含义中取元素组合，但组合方式应符合直觉，让玩家知道为什么会得到这个结果。下文把这一思路整理为设计方法；其中具体技能、命名、数值和界面均是示例或助手提案，不代表用户已逐项选择，也尚未实现或实测。已有用户决定和明确保留的组合优先。

## 1. 先理解含义，不是机械拼字

一个附魔可能同时包含**做什么、针对什么、用什么、在什么情况下发生**。先按原版实际作用和已有跨界含义拆解，再决定本方向分别借用哪些部分；不是按中文名字任意截字，也不能把译名差异当作不同玩法。

例如：

| 附魔 | 可以拆出的含义 | 不能直接假定 |
| :--- | :--- | :--- |
| 爆炸保护 | **保护**是作用；**爆炸**是保护所针对的危险类型。还可以借用爆炸的冲击、扩散形态作为设计意象。 | 原版爆炸保护本身能制造爆炸，或它只意味着进攻。 |
| 冰霜行者 | **冰霜**是主题/媒介；**行走及脚下路径**是行动方式；安全冰路是可选的具象结果。 | 任何寒霜技能都已经完整体现“行者”；任何冰都能直接变水或随意覆盖原水。 |
| 经验修补 | **修补**是结果；**经验**是原版修补的来源。 | 任意修复都已消耗经验，或可以把热量冒充经验球。 |
| 海之眷顾 | 渔获运气、等待与择时；还可以将好运主题转译为符合其他装备操作的选择。 | 在没有鱼钩或真实收线的装备上已经钓到了鱼。 |

并非每个词都有同一种语法结构：忠诚、耐久等更适合从实际用途、代价或动作拆义；数据包新增附魔也须先配置含义和适用对象，不能猜一个名称就产生机制。取出部分含义不要求每次都生硬复刻所有字，但两边应对**实际玩法**有能解释的贡献，而不是只换粒子或名字。

## 2. 允许怎样结合

重点是为每条方向写出**连接关系**，而不是只写两个被选中的词。以下是设计手法，可以混用；不能直接批量套用后就宣称每条都设计完了。

1. **保留对象，改变形态**：保留主位原有的动作或保护对象，让副位改变路径、范围、时机或表现。例如真实防爆之后，将冲击表现成可以释放的寒霜环。
2. **改变用途，并交代转换**：一个附魔提供来源或触发，另一个提供结果。例如将挡下火伤留下的余热用于修补装备；这是耐久奖励，不是产生了经验。
3. **把危险对象转为技能意象**：可以把“被防护的爆炸”借作一次范围冲击的形态，但必须明确告诉玩家它是**融合后的新用法**；它不再自动等同于原版防护。保护和冰霜仍须对玩法有作用，也要说明这是虚拟冲击还是真实世界爆炸。
4. **把副位转成操作节奏**：不要求战斗装备真的会钓鱼；可将浮标、等待和择时化为本装备上的可视节拍。需要真实渔获时仍必须有真实钓鱼事件。

**方向不是死板的词序游戏。** 一般情况下由主位确定行动主体或主要结果，副位改变它；某个方向也可以明确设计为由副位动作提供契机、主位决定结果，但要让玩家看懂，不得覆盖已选专属。反向应重新决定谁提供契机、形态和目标，使操作通常实质不同；用户已决定的“致密 × 破甲正反同效”仍是例外。效果可以是即时变化、持续状态、自动反应或主动选择，不是所有组合都必须积一层“势”再按键。

## 3. 示例：爆炸保护 × 冰霜行者

### 方案 A：防爆冲击凝成霜（现有 53.10 的解释）

- **取词及角色**：爆炸保护取“抵御爆炸”和“冲击”；冰霜行者取“寒霜”，本方向不声称已制造真实冰路。
- **结合方式**：本装备实际减免一次爆炸伤害后，形成短暂霜棱；玩家瞄准释放一次虚拟寒霜环，对合格敌人造成冻结或减速。即“**防爆 → 借冲击凝霜 → 释放霜环**”。这里的“借冲击”是清楚说明的魔法玩法，不是承诺逐点精算物理能量。
- **主位与安全**：保留该载体上适用的基础爆炸减伤；不额外创建真实爆炸、不破地形、不生成水。目标、范围、冷却及实际减伤判定仍待验证。
- **玩家短说明示例**：`受到爆炸并减伤后凝成霜棱，可主动释放寒霜环；不破坏地形。`
- **详细说明示例**：`融合方式：把防爆时的冲击转成寒霜。基础爆炸保护保留；霜环是虚拟效果，不产生水。`

这个方案中的“爆”来自真实危险事件；玩家不必猜为什么冰霜会爆发，也不会误以为这件装备无故放了 TNT。

### 方案 B：把“爆炸”重新解释成霜的释放形态（备选构想，未取代 53.10）

如果希望不必先被炸，也可以提出更自由的重组：玩家真实行走时蓄霜；主动释放时，一圈**虚拟霜爆**向外扩散，对合格敌人造成冻缓，然后余霜收拢成一层抵御下一次爆炸的护幕。这里有意把爆炸保护的“爆炸”由**危险类型**借作**范围释放形态**，把“保护”保留为防爆护幕；冰霜行者贡献霜与行走蓄势。

- 显示方式应直接写明：`行走蓄霜，主动释放霜爆；余霜收成抵爆护幕。` 详情注明**不需要先受到爆炸**，霜爆不是真实爆炸、不破地形、不产水。
- 原本能发生且不冲突的主位爆炸减伤仍保留；同一次伤害的重复防护按该方向合并或替代，不无说明地重复结算。触发频率、范围和护幕收益待设计及实测。
- 这是为解释“爆炸冰霜也可以怎样成立”给出的**另一种助手构想**，不是用户已经选择的玩法，也没有覆盖现有 53.10。若将来采用，需检查与反向的操作区分、适用装备及可实现性。

### 反向怎样不同

现有 **冰霜行者 ▷ 爆炸保护｜冰路缓爆**先由玩家走过本人安全临时冰路蓄霜，再把霜护用于抵御之后的爆炸：`走冰路 → 蓄霜 → 护住自己`。与方案 A 的“先受爆、后释放寒霜”有不同的起手和用途；临时冰只在合法位置形成，消失不生成水。若未来采用方案 B，也要重新对照此反向，避免两边都沦为同一个“走路蓄霜放护盾”。

## 4. 再举一例：火焰保护 × 经验修补

现有 53.19 的助手提案中，**火焰保护 ▷ 经验修补**从前者取“防护火伤产生余热”，从后者取“修补装备”，把余热转成同一件装备的少量耐久奖励；它**不产生经验**。反向则是本人真实经验修补装备后形成修痕，再用于隔热：`真实经验修补 → 隔热护膜`。

这说明可以取“修补”而不强迫制造或消耗经验，但必须把来源和结果说清楚；正常原版主位衔接按该方向记录。它们仍是待验证的提案，不影响用户已选的消耗品经验与补给双收益。

## 5. 每项设计与界面的说明要求

设计记录应写清：**取了哪一侧的哪种含义 → 两者如何连接 → 真实触发或主动操作 → 面向谁产生什么结果 → 成本/时限及原版衔接 → 对象与世界边界**。若核心词发生了用途转变，尤其要指出是怎样转变的；玩家不必查外部文档才能理解。

游戏内可分层呈现，避免每件物品都塞一段论文：

- **短说明**：先说触发、操作和主要结果；有破坏地形、消耗真实资源或严重诅咒时直接标出。
- **展开详情或秘典**：再解释“怎样融合”，列明原版效果保留/合并/替代、真实或虚拟效果、装备适用对象、数值、代价和限制。具体 UI 与输入方式仍待设计。
- **视觉和反馈**：蓄势、可释放、目标和失效要看得见；显示应对应真实行为，不能用炸毁方块的画面暗示无破坏霜环是 TNT 爆炸。

旧总设中仅靠“蓄势”“换形”而无法解释两种含义的条目，要据此继续修订，不因拥有编号或一句取词口号就视为完成。已选专属、明确保留、霜冰不产水、保护原水、真实工具/权限和其他用户约束不因本方法改变。
