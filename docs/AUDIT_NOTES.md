# 26.1.2 审计记录与建议

> 这是源码审计，不是“所有玩法和模组组合都已验证”的认证。**已确认**指代码路径可以直接证实；**风险**指实现存在可触发的危险路径，但影响依服务器、数据包或时序而定；**疑点**需要实测。数值建议遵循本次确定的方向：保留强力玩法，通过明确消耗、冷却与提示管理风险，不做未经验证的大幅削弱。

## 已确认的剩余风险

1. **新掉落归属不明确，可能误处理他人的物品。** `MiningFishingTransmutes.smeltFreshBlockDropsInPlace`、木材转炭和吸附按方块周围范围及实体年龄筛选，而不是追踪这次破坏实际产生的掉落。其他玩家同一时刻的新掉落可能被熔炼、吸附；木制品分支还可能烧掉或改成木炭。多人共享矿场应谨慎或先潜行暂停。建议把捕获范围限定为本次 `playerDestroy` 产生的实体，并测试同时挖掘、物品堆叠、第三方战利品修改和异步生成；不要仅靠更小的半径宣称已解决。
2. **世界修改路径不全走保护事件。** 新冰路/霜封检查原版 `mayInteract`、权限、区块与边界；范围挖掘现在走玩家破坏及 Fabric 事件。但部分霜冰笼、引雷、岩浆以外的世界技能仍会直接设置方块或召唤实体。源码未证明这些操作自动经过所有领地插件的策略；尤其 `AberrantRegistry.placeSingleFrostedIce` 没有玩家上下文。建议引入统一的带操作者权限适配层，并逐项验证领地、出生点保护、冒险模式、PvP 与服务器插件。
3. **范围目标名叫 `nearbyHostiles`，实际并非“仅敌对生物”。** `SignatureRuntimeSupport.nearbyHostiles` 选取排除本人和盟友的活体；未结盟的玩家、村民或动物可能在范围内。雷电也可能通过原版机制引燃或波及其他实体。建议在 UI 继续使用“非友方生物”，并在决定是否改为“仅敌对生物 / 允许 PvP / 可配置目标”前做多人体验测试。
4. **位置相关硬度可能被误判。** `PlayerMiningFusionMixin` 在 `BlockPos.ZERO` 查询 `geyser_bore` 的硬度；对按坐标、方块实体或维度计算硬度的第三方方块可能不准确。该 Mixin 接收的是状态、没有真实目标坐标；应考虑在更合适的有位置调用点计算，并分别验证客户端预测和服务端结果。
5. **超长组件列表会丢弃尾部。** `FusedEnchantmentList.CODEC` 和构造器只保留前 2 对，网络输入最多接受 16 对后同样截断。这让旧/异常物品尽量保留可用数据，但并非无损兼容。若计划提高槽位上限，应先设计迁移、备份和协议版本，不应只改一个常量。
6. **部分技能文案和翻译仍需逐条核验。** 本次修正的是审计中确认偏差的文案，而非对 150 条签名和 116 项化形的每个触发分支完成逐项实测。11 种语言键一致不代表 11 种语言均完成母语翻译；此次修正的部分文本在其他语言暂用英文，建议安排母语校对及真实窄屏/字体测试。
7. **熔炼输出上限值得核验。** `resolveSmeltedStack` 对配方数量乘积使用 99 上限，且未按每个输出物品的最大堆叠数拆分。涉及高产量自定义熔炼配方时，可能截断数量或形成超正常堆叠；应以实际配方和保存/重新加载测试决定拆分方案。
8. **旧潜游路径仍会把原版冰变成水，尚未修复。** `ArmorCurseSignatures` 的 `tide_breaker_dive` 在潜行且可建造时，把脚下所有属于 `BlockTags.ICE` 的方块设置成水；这不只是本模组的临时薄冰，也不等于上表已经处理的临时方块衰变路径。用户已选择下潜时**只移除本模组生成的临时薄冰，不生成水且保留原水/原版冰**；集中实现时应优先修正并测试原版冰、浮冰、蓝冰、霜冰及模组薄冰。现在不能宣称所有冰相关路径已经安全。

## 待验证的疑点与耦合

- **回响可能重复**：`eternal_bowstring` 在常规远程签名和飞行路径相关代码中分别安排回响。是否一次命中会产生两次有效伤害取决于实际触发路径及无敌帧；目前只是源码疑点，需用有/无路径追踪的单目标测试后再决定是否合并。
- **附加伤害与多技能叠加**：部分效果主动重置受击无敌时间、部分使用普通 `hurtServer`。不能仅凭描述断言“每发只允许一个追加伤害”或“完全无视护甲”。建议用伤害记录覆盖弓/弩多射、近战、飞剑、多人 PvP 及伤害免疫模组。
- **可选联动**：JEI/REI 无依赖构建已覆盖；姊妹项目的 `@Pseudo` Mixin、其催化剂、祛魔 UI 及其他版本的 Mod Menu/领地插件并未由当前 smoke 全面实测。升级任一方应以实际安装组合测试，不把软依赖编译通过当作兼容保证。
- **状态寿命**：救命锚点、部分技能冷却和路径记录属于运行时状态，断线或停服后不会等同于持久化能力。锚点区块未加载时不会为救命强制加载；其他特殊地形、危险方块和移动方块仍需游戏测试。
- **兼容接口而非新机制**：`placeIceCage3x3x3` 的旧方块参数历史上即被忽略，目前保留弃用桥接以免直接破坏外部调用；目录中自定义新 ID 也不会自动生成 Java 技能实现。数据驱动映射不等于任意效果脚本化。

## 哪些硬编码值得下一步配置化

优先把**服务器平衡/治理决策**从代码中提取为有范围、带版本和默认值的数据，而不是把所有常量都暴露成滑块。下表为建议，当前仍以源码为准：

| 当前硬编码 | 建议 | 原因 / 注意 |
| :--- | :--- | :--- |
| 忠诚救命 `20` 耐久、`600` tick 冷却、每 `60` tick 修 1 点；贪婪黑洞消耗 3 点经验 | 增加按技能分组的消耗/冷却字段，显示单位与有效范围。 | 通用 `trigger_cooldowns` 不会覆盖所有技能自己的冷却；避免管理员误以为一个配置控制全部。 |
| 霜冰首次 `24–48` tick、后续 `20–36` tick；冰路半径上限 4 | 可配置生命周期/覆盖半径，设置严格上限并保留“只替换空气、不产生水”的不变量。 | 过长寿命和大量方块更新可能影响性能或困住玩家；修改需要重启/卸载区块测试。 |
| 自动熔炼搜索半径 `1.9`、新掉落年龄 `≤2` tick、木炭概率 `65%/100%` | 优先解决掉落归属，再考虑可配置概率、经验和扫描限制。 | 仅配置半径不能保证隔离其他玩家物品；概率应在 UI 标明。 |
| 范围效果半径、持续时间与实体筛选散落在签名处理器 | 按技能分类逐步配置，增加服务端边界、同步版本与兼容默认值。 | 先确定玩家/PvP/中立生物策略；不要悄悄弱化全部效果。 |
| 部分兼容性的物品 ID 与旧别名 | 集中维护版本/集成表并建立联动测试，而不是每个调用点自行猜测。 | 外部模组 ID 是兼容契约，改名须有迁移路径。 |

反例：**网络包大小上限、组件槽位上限、协议 ID、资源路径和必需 Mixin 目标**是安全或兼容契约，不宜作为普通服主平衡配置随意改动。提高它们需要编解码、存档、客户端/服务端版本协商及迁移测试。

## 数值与机制的中肯建议

- 默认互斥碰撞为 45%；三枚普通稳定晶依次降至 32%、19%、8%。这个不可降至零的普通下限和默认 3 晶 + 25 级的净化代价会显著增加容错成本；适合作为高风险设计，但应让服务器根据节奏配置，而不是暗示稳定晶必然保底成功。
- 高阶非互斥签名 28%、非签名 22%，中阶从 18% 起按等级和增加；不要把所有“高阶”与互斥的 8% 底线混为一谈。强化配置界面的报价和失败结果，比统一砍低效果更能帮助玩家做选择。
- 忠诚救命每 3 秒修 1 点、每次救命耗 20 点且冷却 30 秒；约 60 秒的被动修复即可抵回一次消耗，和经验修补叠加后可能非常持久。保留当前强度，但建议让服主分别调整恢复速度、耗耐久和冷却，并区分“锚点不可用”提示。
- 狂血反噬追加 4.5 点魔法伤害，28% 概率自损 1 点；从简单期望看自损只有每次 0.28 点（未计抗性、触发频率、无敌帧等），对高频攻击可能仍然偏强。应先测吞吐与实际生存代价，再决定是否调整消耗或冷却。
- 高强度范围挖掘现在逐格消耗耐久、触发普通掉落与保护事件；建议观察时运、精准采集、末次耐久、背包满载及服务器负载，不要在没有测量前额外缩小范围。

## 验证范围与仍需手测

- 仓库 CI 针对提交运行静态检查、Gradle 构建、JUnit、关闭 JEI/REI 的编译，以及 26.1.2 专用服务器和真实客户端/集成服务器 smoke。范围挖掘 smoke 覆盖正常工具掉落与耐久、事件取消、防递归、末次耐久和成熟作物；临时冰 smoke 覆盖保水、破坏/自然消散及实体碰撞移动。以对应提交的 Actions 结果为准。
- 本机环境没有 Java 且不能直连所需 Maven；Java 编译与实际游戏 smoke 由 GitHub Actions 执行。自动 smoke 不替代人工操作、截图质量评审或长时间多人性能测试。
- 仍建议人工验证：远程专用服务器两名玩家同时操作、真实第三方领地/PvP 插件、姊妹模组完整联动、水流与船/不同体型实体、区块卸载/重启后残留方块、复杂资源包及 11 语言的换行和字体。
